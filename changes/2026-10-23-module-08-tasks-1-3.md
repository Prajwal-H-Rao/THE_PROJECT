# 2026-10-23 — Module 08 tasks 1–3 — Policy rule schema, family defaults, decision endpoint

## Scope

Module 08 (Policy and approval engine) tasks 1, 2, 3 per build order:
1. Define the policy rule schema: actor, scope, sensitivity, target, blast radius, risk tier
2. Encode per-action default policies for all 7 task families in `families.yaml`
3. Implement the decision endpoint returning `allow`, `deny` or `needs_approval`

### Policy module: `src/policy/`
- `policy-schema.ts`: TypeScript interfaces for PolicyRule, PolicyDecisionRequest/Response, Sensitivity, BlastRadius, RiskTier, Decision. Validation functions `validatePolicyRule()`, `validateDecisionRequest()` that reject unknown fields.
- `families.yaml`: 7 task families (inbox, calendar, tasks, finance, trips, jobs, channels) with 18 rules total. Each rule has id, actor, scope, sensitivity, target, blastRadius, riskTier, defaultDecision, version. High-sensitivity actions (send, invite, import, apply, link) require `needs_approval` and `requiresStepUp: true`.
- `policy-loader.ts`: `loadFamilies()` validates YAML, `findMatchingRule()` selects most specific rule by action match then scope match, preferring higher risk tier.
- `policy-decision.service.ts`: `decide(request)` returns allow/deny/needs_approval. For `needs_approval`, generates nonce bound to payloadHash. Deterministic for same input. `getAllRules()`, `getRule()`, `getFamilies()`, `validateFamilies()`.
- `policy.controller.ts`: REST endpoints:
  - `POST /policy/decide` — policy decision
  - `GET /policy/rules` — all rules
  - `GET /policy/rules/:ruleId` — specific rule
  - `GET /policy/families` — all families
  - `GET /policy/validate` — family validation
- `policy.module.ts`: exports PolicyDecisionService
